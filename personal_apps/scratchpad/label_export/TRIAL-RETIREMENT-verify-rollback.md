## ROLLBACK lens — concrete risks

Verified against the working tree at `C:/Users/michi/Desktop/CodingStuff/personal_apps` and against deployed `main` (`b1d1a7c`) via `git show`.

### A. The goal is not reachable through any supported path

**R1. No state exists in which the judgments survive *and* retention resumes.**
`retention_floor` returns a floor whenever `status in PINNING` (`features/radar/judge_trial.py:157-170`, `:44` — armed/running/recovering). The only writer of `RECOVERED` is `_release_if_drained` (`:557`), gated on `_recoverable(state).count() == 0` (`:553-556`) — i.e. on every encoder-stamped mention having been nulled. A *passing* audit deliberately keeps pinning (`:162-166`, echoed `features/radar/retention.py:32-36`). So "retire without undoing" means leaving the row in a PINNING state permanently, and `retention._pinned` (`retention.py:23-46`) then caps `prune_posts` (`:232-233`) and `prune_mention_events` at `retain_from` ≈ 2026-09-04 forever. Journal rows are normally kept 48h (`features/radar/config.py:610`), posts 30 days (`:603`); the prune job runs once daily at 04:30 (`run_radar_ingest.py:1373`). The runbook already predicts ~5 extra days of journal for a bounded 10-day trial (`docs/superpowers/plans/2026-09-06-radar-encoder-judge-runbook.md:226-244`) and asks for daily `df -h`. An unbounded trial has no such bound, on an 8 GB box whose journal already needed a forced index once. **This destroys nothing today and forecloses everything later:** the exit from that state, whenever disk forces it, is still the destructive one, and every extra day of judging makes it bigger.

**R2. The row cannot be removed, and removing it by hand is the most one-way action in the plan.**
`arm_trial` refuses a second row (`judge_trial.py:247-250`); `judge_config._encoder_or_none` refuses a deployed bundle whose hash differs from the armed one (`judge_config.py:179-184`). So the base artifact cannot run while this row exists. There is **no delete path anywhere** — `grep RadarJudgeTrial` over `features/`, `scripts/`, `models.py` yields only `judge_trial.py:32,134,251,351,738` and `models.py:1382`; `manage_encoder_trial.py:144-171` exposes only `status`/`arm`/`stop`/`tick`. Manual `DELETE FROM radar_judge_trial WHERE id=1` then: (a) makes every small-model judgment permanently unrecoverable, because `_recoverable` selects by the *row's* frozen `model_id`/`prompt_version` (`judge_trial.py:333-337`) and `recover_trial` raises "no trial record" without it (`:452-454`); (b) makes `_may_judge` raise on `row is None` (`:675-679`) → `ConfigError` (`judge_config.py:178`) → the **whole `radar_ingest` daemon fails to start**, uncaught by design (`run_radar_ingest.py:1258-1275`). The DELETE must ship in the same window as a code change or radar goes dark. It has no dry run, no report, no confirmation, and no test.

**R3. After this plan there is no undo mechanism at all, ever.** Whatever route is taken, the end state is an encoder judging live with the pin released or the row gone. The journal is back to 48h, so "the base model removed the wrong things for a week" has no remedy short of a DB restore. That is defensible — but it is the thing `judge_trial.py:1-22` was written to prevent, and it should be decided explicitly rather than arrived at.

### B. The destroy button is live, one command, and mis-documented

**R4. `stop` is not a pause.** `cmd_stop` (`manage_encoder_trial.py:117-123`) writes two columns (`judge_trial.py:297-299`) and prints *"the decisions already made are still in the counts until recovery runs"* (`:120-122`); the runbook repeats *"the first alone is not a rollback"* (`runbook:396-400`). **Both are false on the deployed layout.** `deploy/radar-encoder-trial.timer` fires `OnCalendar=*-*-* *:*:00` with `Persistent=true`, driving `ExecStart=… manage_encoder_trial tick --limit 2000`, and `tick()` calls `recover_trial(apply=True)` unconditionally for `RECOVERING` (`judge_trial.py:796-801`). Destruction begins within 60 seconds, 2000 mentions/minute, unattended. The documented "look before you leap" dry-run step (`runbook:406-409`) does not exist wherever the watchdog is installed — which is where it is installed. Nothing in the repo disables that timer as part of any procedure.

**R5. A recovery in progress cannot be aborted.** No writer transitions `RECOVERING → RUNNING`; `recover_trial` raises if it observes any other status mid-drain (`judge_trial.py:498-501`), `note_first_judgment` refuses to revive (`:776-778`), `request_stop` only sets RECOVERING (`:297`). So a half-drained trial is the worst state available — half the verdicts undone with their windows rebuilt, half still in force — and the only forward move is finishing the destruction. The frame was 6,207 mentions in the first 24h (handover §3), so at 2000/min the whole thing is over in minutes, not hours: there is no window to notice and intervene.

**R6. `accept` on the failing report is irreversible twice over, and it is the documented next step.** A failing report is a valid result, recorded and acted on (`audit_encoder_trial.py:946`; `judge_trial.py:606-607`, `:657-660` sets RECOVERING + stop_reason → watchdog drains). It *also* permanently closes the audit: once `audit_evaluated_at` is set, a different report is refused (`judge_trial.py:637-641`), so a corrected/supplemented passing report can never be accepted for this trial. The situation is recoverable today **only because nobody has run `accept`** — and it is the last command in runbook §10 (`runbook:465-467`). Treat it as a protected command for the duration.

### C. Time — and a seven-day error sitting in the working tree

**R7. The checked-out branch lies about the deadline.** Deployed `main` carries `AUDIT_DRAW_DAY = 1`, `AUDIT_LABEL_DAY = 2`, `TRIAL_DEADLINE_DAYS = 3` (commit `d745e8e`, "shorten the live encoder trial to a 1/2/3-day audit schedule"). The checked-out `dev_personal` still carries `3 / 7 / 10` (`personal_apps/features/radar/judge_trial.py:575-577`); `git log main --not dev_personal` shows `d745e8e` and `13c9fce` are missing from it. Anyone computing the deadline from the working tree gets `first_judged_at + 10d` = **2026-09-16** instead of the real **2026-09-09 19:38 UTC** — seven days of imaginary runway on the one clock whose expiry destroys data.
Second-order, and worse: `cmd_accept` reads `judge_trial.AUDIT_DRAW_DAY/AUDIT_LABEL_DAY` from *whatever checkout runs it* (`scripts/audit_encoder_trial.py:930-943`). Run the corrected audit chain from a `dev_personal` checkout and the day-1 draw falls before "day 3" and `accept` refuses the report outright — the audit becomes unacceptable purely because of the branch it ran from. Nothing documents that the chain must run from the deployed commit. And any edit to `judge_trial.py` on `dev_personal` risks a merge that silently restores 3/7/10 into main, extending a trial main deliberately shortened.

**R8. `PROMPT_VERSION` is an unmarked one-way lever.** `llm_sentiment.py:69`. Bumping it — a plausible instinct when swapping models — makes `_may_judge` refuse (`judge_trial.py:686-690`) → dead daemon, *and* makes every existing encoder row permanently unrecoverable (`_recoverable` filters on the frozen version, `:333-337`). There is no warning near the constant.

### D. What recovery destroys that no one lists

**R9. Recovery is not a restore, even for what it touches.** Five mention columns nulled with no archive (`judge_trial.py:511-515`) — and if an encoder verdict had overwritten an earlier judge's, recovery nulls to *unjudged*, it does not restore the predecessor, which exists nowhere on the mention. Buckets and bucket-sources are overwritten **in place** from the current journal (`:527` → `buckets.py:438-462`); `RadarBucket` is retained forever and unversioned, so the counts as they stood are gone. `chatter_decided_at` is clobbered with the recovery timestamp (`journal.py:243-244`). `promoted` flags are reset (`buckets.py:415-416` → `journal.py:170-205`). Conditional but real: if `source_config_version` has moved by then, `buckets.py:449-457` NULLs `expected`/`variance`/`mention_z`/`baseline_days` for **every child in every rebuilt window** — blanking the board's magnitude axis across days of history. The only true restore is the nightly mysqldump, which rolls back the entire DB including every mention, quote, price and watch mark written since — and the runbook never mentions it as the fallback it actually is.

**R10. Encoder tone survives every recovery path, and there is no switch for it.** `EncoderBackend.writes_tone = True` (`judge_backends.py:210`); `apply_judgments` materializes `sentiment_attitude`/`expected_move`/`confidence`/`llm_sentiment`/`sentiment_tone_model` (`llm_sentiment.py:494-502`). `recover_trial` clears none of it while its docstring asserts "The trial never wrote them" (`judge_trial.py:444-446`), `scripts/rollback_encoder_judge.py:22-23` repeats it, and the regression test pins the behaviour with `sentiment_tone_model='claude-haiku-4-5'` (`tests/test_radar_judge_trial.py:626-645`) — the pre-09-07 world. A "complete" recovery therefore leaves encoder attitude in force with `sentiment_model` NULL beside it, and `board.py:358-368`'s bull/bear CASE reads `sentiment_attitude` first. **There is also no config-level partial rollback:** `Settings.write_encoder_tone` is written and never read by any production path (`judge_config.py:44`, `:102` — grep finds only those two plus test asserts), and `RADAR_JUDGE_TONE` *refuses* any value but `'0'` (`:89-97`) under a comment claiming encoder tone never reaches a reader. "Keep base judging relevance, stop it publishing tone" is a code edit and a redeploy, not a flag.

### E. The small artifact — preserved by accident

**R11. It exists, in a directory designed to be deleted.** `personal_apps/artifacts/` is fully gitignored (`.gitignore`, with only `!personal_apps/artifacts/.gitkeep`) and the repo copy is empty. But the exact audited bundle **is** on this machine: `C:\Users\michi\Desktop\CodingStuff-worktrees\radar-encoder-judge\personal_apps\artifacts\judge\`. I recomputed `judge_backends.bundle_sha256`'s algorithm (`judge_backends.py:224-244`) over its `v1/{model.onnx,tokenizer.json,config.json}` and got `3bb32b5607a8a368d8ff72179b41de00c6a971223bbed21302e95dcfb90dccb5` — matching the armed trial's `3bb32b5607a8a368…`. That is *the* rollback asset, it is undocumented, and it sits in a gitignored path inside a worktree for feature work already merged to main. `git worktree remove`, `git clean -xdf`, or a tidy-up of `CodingStuff-worktrees/` destroys it. Nothing names it as a protected file.

**R12. It cannot be reliably recreated.** `package_encoder_artifact.py` writes `packaged_at_git_head` into `config.json` (`:189-196`) — so `config.json`'s bytes, and therefore the bundle hash, change on *every* repackage even from identical weights, before you get to `torch.onnx.export` (`:170-178`) and a re-downloaded `tokenizer.json` (`:181-186`) being non-reproducible across library versions. A repackaged small model will not match `artifact_sha256` and `judge_config.py:179-184` will refuse to start the daemon against the armed row. **Rollback to the small model is byte-exact-copy-or-nothing while the row exists.** Handover §9 item 5 asks whether rollback "is one command": today it is one `scp` of a directory no procedure protects, and it is not one command if that directory is gone. (The source checkpoints do survive — `radar_labels/encoder/model-train13000/weights.pt` for small, `model-train17090-20260907-192428/weights.pt` for base — so the *model* is recoverable even if the *artifact* is not.)

**R13. The packaging tool cannot produce a side-by-side version, and the documented deploy overwrites the old one.** `version_dir = os.path.join(args.out, 'v1')` is hardcoded (`package_encoder_artifact.py:130-131`) and `active.json` is always written as `{"path": "v1/"}` (`:196-199`) — no `--version` flag. Packaging base into the same root overwrites `v1/*` in place. The runbook's deploy is `scp -r artifacts/judge root@…:/root/coc-stats/personal_apps/artifacts/` (`runbook:199-201`), a recursive merge that overwrites the VPS's `v1/*` too — **and it still names the decommissioned box `82.165.240.212`** while prod is `194.164.29.97` (handover §2), so followed literally it writes base onto the fallback, which may hold the only other copy of small. A `v1`=small / `v2`=base layout with a pointer flip requires manual `mkdir`/`mv` plus hand-editing `active.json`. That is the difference between rollback = "edit one JSON, restart" and rollback = "566 MB transfer under incident conditions".

**R14. An in-place swap on a live daemon fails late and detached, and can corrupt the running process.** `bundle_sha256` is called only at startup (`judge_config.py:179-184` via `run_radar_ingest.py:1275`); the ONNX session is built on first batch and held for process lifetime (`judge_backends.py:318-347`). Overwriting the files under a running daemon looks like nothing happened — it keeps judging with the old weights — until a restart hours or days later kills *all* of radar ingest (no fetch, no scoring, no quotes, no pruning), not just judging. And onnxruntime holds `model.onnx` mapped; `scp` truncating and rewriting the same inode under a live process risks garbage inference or SIGBUS, with no checksum on the read path to catch it.

**R15. After a base deploy under the same id, selective rollback is impossible.** `_validate` checks only files, `max_len` and head names/class order (`judge_backends.py:258-302`); `config['base']` is written (`package_encoder_artifact.py:195`) and never read at runtime. Hidden size, layers and vocab are never inspected. Every base row will be stamped `radar-encoder-v1` (`judge_backends.py:215` → `llm_sentiment.py:497`), identical to every small row in both `radar_mentions.sentiment_model` and `radar_sentiment_judgments.model` (`models.py:1339`). **No query can then separate what small judged from what base judged**, so "undo only the base model's week" is impossible after the fact — the only discriminator is `created_utc` against a deploy timestamp that must be recorded deliberately. Changing the id to distinguish them makes the armed trial refuse to start (`judge_trial.py:682-685`). This is the exact trap the codebase already fell into once — `stored_row_carries_tone` exists because "one id could not tell them apart" (`llm_sentiment.py:431-441`) — and the plan re-enters it. **Record the swap timestamp in the DB or a file before the restart; it is the only forensic handle that will exist.**

### F. Corrections to the readers

- **`accept-path` is wrong about production timing.** It cites `AUDIT_DRAW_DAY = 3` / `AUDIT_LABEL_DAY = 7` at `judge_trial.py:575-576` and reasons throughout about "day 3" and "day 7". Those are `dev_personal` values; deployed `main` runs **1 / 2 / 3** (`d745e8e`). Every timing conclusion in that note describes a checkout that is not in production. Its `TRIAL_DEADLINE_DAYS` reasoning is likewise off by seven days.
- **`stop-semantics` is right on the tone premise** — I confirmed `writes_tone = True` (`judge_backends.py:210`), the un-cleared columns (`judge_trial.py:511-515`), and that the regression test stages Haiku as tone owner (`tests/test_radar_judge_trial.py:626-645`). Its wedged-`RECOVERING` trap is real *as a no-exit state* but effectively unreachable: `refuse_outside_retention` (`judge_trial.py:745-758`) and `run_pass` clamping `since` to `retain_from` (`llm_sentiment.py:797-800`) keep out-of-pin windows from existing. Present it as "if it happens there is no way out", not as a likely failure.
- **`artifact-gate`'s `anthropic:radar-encoder-v1` "escape hatch" is a dead end** — the `AnthropicBackend` would carry `radar-encoder-v1` as its *API model name* and 404 on the first call. It should not be listed among the ways to get encoder-labelled rows.
- **`deploy-swap` misses the preserved bundle.** Its "the artifact is not in git, the only complete artifact in the repo is the 12 KB test fixture" is true but incomplete: the byte-exact armed bundle is in the sibling worktree (R11). That single fact changes the rollback story from "must repackage and re-arm" to "must not delete one directory", and it is the most important operational fact in this whole review.
- Minor: several `judge_trial.py` line citations across the notes are off by 1-3 against the working tree (e.g. `accept_audit` is at `:602`, the schedule constants at `:575-577`). Harmless, but line-anchored claims should be re-checked against the *deployed* file, not this branch.
